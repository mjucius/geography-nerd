# T-015: Compact city data and loader, drop capitals

## Acceptance
- All ~1,000 cities of `data/cities-import.sql` ship in one compact data file, each with a sitelink count, no larger per city than today's (brief 1).
- `is_capital` is still carried in the data and loader (T-016 removes it with the filters that use it), so levels 1-5 still have cities.
- `npm run generate:local-cities` rebuilds the data from the SQL and the sitelinks file.
- The game plays as before for now (levels not yet changed).
- `npm test` and `npm run lint` pass.

## Plan
Files: `scripts/generate-local-cities.mjs` (rewritten output), new `web/src/data/cities.json` (generated, committed), `web/src/data/localCities.ts` (becomes a hand-written loader, no longer generated), `web/src/types/index.ts` (`City` gains `sitelinks: number`), `web/src/test-fixtures.ts` (add `sitelinks` to the fixture cities if they are typed `City`), `web/src/services/__tests__/cityDataService.test.ts` (data tests), docs that name the generated file: `README.md`, `web/README.md`, `CONTRIBUTING.md`, and the two console messages in `scripts/import-cities.mjs`.
Approach: the generator reads `data/cities-import.sql`, `data/countries.sql` and `data/city-sitelinks.json`, and writes `cities.json` as `{ "countries": { "FR": ["France", "Europe"] }, "cities": [["Paris", "FR", 2138551, 48.85341, 2.3488, 366, 1]] }`: name, country code, population, lat, lon, sitelinks, then a 0/1 capital flag. The flag is the old `is_capital` and stays in this ticket only because the current level filters still read it; T-016 removes it with the filters (the capitals still come from the second INSERT in the SQL, which is what the generator does today). The generator takes all cities (no `.slice(0, 100)`), fails loudly if a city has no sitelink entry, and writes with no indentation, one city per line so diffs stay readable. `localCities.ts` imports the JSON and maps each row to the existing `City` shape (`id` = row number, `countries` from the map, `location` as `[lon, lat]`, `region`, `is_capital`, new `sitelinks`), so no component changes. To keep behaviour the same, `getCitiesByDifficulty` filters `LOCAL_CITIES.slice(0, 100)` (the original 100, the first 100 SQL rows) instead of all 1,000, because filtering before the top-100 cut would grow the capital levels' pools from 28 to 43 cities. A comment marks the slice as temporary; T-016 replaces the whole function with the level table.
Tests (in `cityDataService.test.ts`, existing tests stay): `LOCAL_CITIES` has 1,000 cities with unique ids and a positive `sitelinks` that equals `data/city-sitelinks.json` for that name and country; Paris hydrates to id, country name "France", region "Europe", `location.coordinates` `[2.3488, 48.85341]`; `cities.json` is at most 430 bytes per city (today's `localCities.ts` is 43,012 bytes for 100 cities); and a regression test per level (1 to 10) that the ids returned by `getCitiesByDifficulty` equal a frozen list of the ids it returns today. I record those lists now from the current code, before changing anything, and paste them into the test. The ids are stable because rows keep SQL order, so the first 100 ids are the original 100.
Prove tests can fail on a copy outside the repo: cut the generator to the first 999 cities and regenerate (count test red); swap lat and lon in the loader (Paris test red); read sitelinks from the wrong column in the loader (sitelinks match test red); add indentation to the generator (size test red); remove the `.slice(0, 100)` in `getCitiesByDifficulty` (the capital levels' regression tests go red). Run `npm run generate:local-cities` and confirm it leaves `cities.json` unchanged (so the committed file is reproducible), `npm test` and `npm run lint` and `npx tsc -b` in the foreground, reading exit status. If tsc objects to the JSON import, I add `resolveJsonModule` to `tsconfig.app.json`.
