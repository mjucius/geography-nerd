# T-014: Fetch Wikidata sitelink counts for the cities

## Acceptance
- A script `scripts/fetch-sitelinks.mjs` (one-time, by hand) looks up every city in `data/cities-import.sql` on Wikidata and writes `data/city-sitelinks.json` with a sitelink count per city (brief 1).
- The committed file covers all ~1,000 cities; the script reports any it could not match and `data/wikidata-overrides.json` fixes those, so none are missing.
- Matches are checked by location, so a famous namesake elsewhere is not picked (for example Paris, Texas for Paris, France).
- The game makes no network call for this at runtime.
- `npm test` and `npm run lint` pass.

## Plan
Files: new `scripts/fetch-sitelinks.mjs` (network and file I/O) and `scripts/sitelinks-match.mjs` (pure `haversineKm` and `pickCandidate(city, candidates)`, imported by the script and by the test), new `data/city-sitelinks.json` and `data/wikidata-overrides.json`, `package.json` (script `fetch:sitelinks`), `scripts/generate-local-cities.mjs` untouched (T-015 reads the file). Tests: a vitest test in `web/src/services/__tests__/citySitelinks.test.ts` reads the committed JSON and the SQL.
Approach: parse the cities (name, country, lat, lon) from the SQL with the same regex the generator uses. For each city, call `wbsearchentities` (name, language en, limit 10), batch the candidate QIDs into `wbgetentities` (props `claims|sitelinks`, 50 per call), keep candidates that have a P625 coordinate within 40 km of the city (haversine), and take the one with the most sitelinks. An override in `data/wikidata-overrides.json` (`"name|CC": "Qnnn"`) skips the search. Output is `{"name|CC": {"qid": "Q90", "sitelinks": 300}}`, sorted by key, so diffs are stable. Requests run one at a time with a short delay and a User-Agent naming the repo, per the Wikidata API etiquette; failures retry 3 times. The script prints unmatched cities and the lowest and highest counts, and exits non-zero if anything is unmatched. I run it, fix the unmatched ones through overrides (looking each up on Wikidata), and re-run until it exits 0. Spot-check by hand: Paris is Q90 (not Paris, Texas).
Tests (`npm test`, no network): the committed JSON has a positive integer count and a QID for every one of the 1,000 cities in `data/cities-import.sql`, with no extra keys. The test also pins Paris to `Q90`, a city that is in the SQL. A second, offline test calls `pickCandidate` with a city at Paris, France and two candidates: a distant namesake (Paris, Texas) with more sitelinks and the local one with fewer. It must return the local one, and return null when no candidate is within 40 km. This proves the location check, not just the data.
Prove the test can fail: on a copy outside the repo, delete one key from the JSON and see it go red; change Paris's QID and see it go red; remove the distance filter in `pickCandidate` and see the namesake test go red. If vitest or tsc objects to importing the `.mjs` from `web`, I'll add a minimal declaration next to the test rather than move the code.
Run `npm test` and `npm run lint` in the foreground and read the exit status.
