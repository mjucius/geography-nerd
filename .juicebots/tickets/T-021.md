# T-021: Script that flags sub-city entries from Wikidata classes

## Acceptance
- A script reads the Wikidata instance-of classes of every shipped city (the committed QIDs minus `data/excluded-cities.json`) and writes a committed report `data/subcity-flags.json` with each city's class QIDs, class labels and a tier. A city is flagged when any of its classes is a strong sub-city class; a city whose only sub-city-like classes are weak ones is marked for review; every other city is unflagged (brief 11, how the list is built; pm agreed this detection rule, since an "only sub-city classes" rule misses Eixample, South Boston and Tuggeranong).
- The report flags every example named in the brief (Eixample, Hamburg-Nord, Sector 4, Gustavo A. Madero, South Boston, Tuggeranong Administrative District) and does not flag Brampton, Yokohama, Giza or Quezon City. An offline test re-runs the classifier on the committed class QIDs and checks it agrees with the committed tier, so a classifier change fails the test without regenerating the report.
- The game does not read the report and makes no network call.
- `npm test` and `npm run lint` pass.

## Plan
Files: new `scripts/flag-subcity.mjs` (network and file I/O), new `scripts/subcity-classes.mjs` (the class lists and a pure `classify(classIds)`, imported by the script and by the test), `package.json` (`flag:subcity`), new committed `data/subcity-flags.json`, new test `web/src/services/__tests__/subcityFlags.test.ts`, `CONTRIBUTING.md` (one line). No app change.
What I found when I looked at the real Wikidata classes (994 cities): the brief's rule "flag a city whose classes are only sub-city classes" would miss three of the brief's own examples, because Wikidata lists mixed classes: Eixample is `district of Barcelona` and `ensanche`, South Boston is `town` and `neighborhood in Boston`, Tuggeranong is `district of the Australian Capital Territory` and `district`. So the script uses two tiers instead: **flagged** when any class is a strong sub-city class, meaning a class that names a part of a specific city or a plainly sub-city kind (sector of Bucharest, borough of Hamburg/New York City, London borough, district of Barcelona/Madrid/São Paulo/Moscow, territorial demarcation of Mexico City, quarter of Hamburg, neighborhood and neighborhood in Boston, city district, local government area (all variants), suburb, raion of city in Ukraine, district of the Australian Capital Territory, and similar); **review** when it has only weak classes that are sub-city in some countries but ordinary places in others (district of Turkey, district, urban district of a German state, unparished area, administrative divisions of Russia). Real cities with a mixed list stay unflagged (Brampton, Yokohama, Giza, Quezon City, Lexington). The final decision stays a manual review (T-022); the report just makes it fast.
Approach: read the QIDs from `data/city-sitelinks.json` for the shipped cities (SQL keys minus `excluded-cities.json`), fetch each QID's P31 values in batches of 50, fetch the English labels of the classes, and write `data/subcity-flags.json` as `{ "classes": { "Q123": "label" }, "cities": { "Name|CC": { "tier": "flagged" | "review" | "", "classes": ["Q123", ...] } } }`, sorted by key, with one city per line. Same API etiquette as the sitelinks script (User-Agent, one request at a time, retries). The class lists are QID sets in `subcity-classes.mjs`, each with its label as a comment so a reviewer can read them. After the first run I print every class that has no tier and was used by a city whose name looks like a district (`Sector`, `District`, `-Nord`, `Borough`, `Ward`, `Distrito`, `Arrondissement`), and extend the lists from that, so the first pass is not guesswork.
Tests (`subcityFlags.test.ts`, offline): `classify` flags `[district of Barcelona, ensanche]`, `[town, neighborhood in Boston]` and `[district of the ACT, district]`, marks `[district of Turkey, town, municipality of Turkey]` as review, and leaves `[city, big city]` unflagged; on the committed report, `classify` applied to every city's stored class QIDs equals its stored tier (this is what makes the classifier mutations below fail), and Eixample, Hamburg-Nord, Sector 4, Gustavo Adolfo Madero, South Boston and Tuggeranong Administrative District are all `flagged`, and Brampton, Yokohama, Giza and Quezon City are all unflagged; the report covers exactly the shipped cities (SQL keys minus excluded ones).
Prove tests can fail on a copy outside the repo: remove `ensanche`-style tolerance by making `classify` require all classes to be strong (the Eixample test red); empty the strong list (with the class QIDs stored in the report the classifier is re-run offline against the committed tier, so this goes red without regenerating anything); move `city` into the strong list (the Brampton unflagged test red); delete one city from the committed report (coverage test red).
Run the script once for real and report the tier counts. Run `npm test`, `npm run lint`, `npx tsc -b`, `npm run build:web` in the foreground and read exit status.
